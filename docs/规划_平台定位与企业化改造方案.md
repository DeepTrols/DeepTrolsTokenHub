# 智曜TokenHub 平台定位与企业化改造方案

> 文档性质：总体规划与目标态设计文档。基于 2026-09-02 全仓审计与五项产品决策制定，
> 作为后续各阶段实施与验收的基准。与本文冲突的旧表述以本文为准。
> 版本：v1.0　日期：2026-09-02
> 范围：定位与边界 / 企业化管理 / 动态 RBAC / 支付自接 / 落地页接口 / 路线图

---

## 1. 背景与目标

### 1.1 审计结论摘要

2026-09-02 全仓审计确认：核心平台（Go 后端 + React 控制台）已达生产级质量
——计费引擎（Reserve-Settle/Commit-Release + 乐观锁 + 幂等 + 全链路 decimal）、
五不变量证据链、安全基线（生产配置 fail-fast、httpOnly Cookie、限流）与文档同步度均良好。

同时确认以下结构性事实，构成本方案的设计依据：

| 现状 | 证据 | 规划含义 |
|---|---|---|
| 租户解析已脱离 Host 域名，改为从账号 membership 解析 | `internal/handler/middleware/auth.go`（"no per-tenant custom domains"） | 单域名部署模式已成立，去 OEM 化的最大技术风险已消除 |
| 企业数据层已存在：`tenants`（信用代码/执照字段）、`tenant_memberships`（owner/admin/member）、`tenant_invitations`（令牌邀请）、5 状态审核状态机 | migrations 000001 / 000005 | 企业管理不缺数据模型，缺 API 与流程 |
| 注册只支持个人：`userType` 硬编码 `personal`，无企业自服务 API | `internal/handler/console/auth.go` `HandleRegister` | 企业管理是从零建 API 层，不是改表 |
| 平台权限仅 `users.role: user\|admin`，全有全无 | migration 000002 | RBAC 需新建权限体系 |
| 支付已有 `Gateway` 接口抽象（"epay first, official adapters later"）；`payment_orders` 状态机完备；入账以 `order_no` 做幂等键 | `internal/service/payment/types.go`、migration 000022 | 自接支付是替换适配器，不是重写支付系统 |
| 支付宝/微信官方 SDK 已在依赖树（go-epay 间接引入） | `go.mod` | 直连无需新依赖源 |
| 公开接口已存在：`/api/public/pricing`、`/site`、`/rankings`、`/stats` | `cmd/api/main.go` | ai-nuxt 落地页数据源已存在，缺对接 |
| 网关扣费固定用个人钱包 `FindByUser(userID, nil)`；`tenant_id` 已进证据链与定价链路 | `internal/handler/gateway/chat.go` | 企业共享钱包只需改「钱包解析」入口 + 新建企业钱包存储 |

### 1.2 改造目标

将平台从「OEM 多租户聚合系统」收敛为「单一运营方、面向个人用户与企业用户的
AI 模型聚合服务平台」：

1. **去多渠道化**：渠道只归平台运营方，租户概念重定义为企业客户；
2. **补齐企业管理**：企业创建/人工审核、成员邀请、共享钱包、用量账单；
3. **补齐权限管理**：管理后台动态可配置角色（不写死），企业内三级角色；
4. **支付自接**：移除易支付，直连支付宝/微信官方接口；
5. **落地页对接**：ai-nuxt 营销站接入真实公开数据。

## 2. 产品定位与边界控制

### 2.1 一句话定位

> 单一运营方的 AI 模型聚合服务平台：平台方自营上游渠道，向**个人用户**和
> **企业用户**售卖模型调用额度，提供统一计费、用户控制台与运营管理后台。

### 2.2 三种角色、两种界面

```
平台运营方（我们）      → 管理后台（/admin：渠道、模型、定价、企业审核、财务、对账、角色、系统配置）
个人用户（付费调用者）   → 用户控制台（注册、充值、API Key、用量、账单）
企业用户（组织客户）    → 用户控制台 + 企业中心（企业认证、成员、共享钱包、企业用量）
```

### 2.3 边界红线（明确不做）

- ❌ 租户自定义域名 / 独立站点（OEM 白标）
- ❌ 租户自有渠道 / 转售分销（渠道只归平台运营方）
- ❌ 租户级品牌配置、结算配置、模型选品
- ❌ 「平台租户」概念对普通用户可见

### 2.4 存量功能裁定表

| 存量能力 | 裁定 | 处置 |
|---|---|---|
| `tenants` 表及审核状态机 | ♻️ 重定义为「企业客户」 | 保留；产品术语统一为「企业」，代码层暂留 `tenant` 命名（避免触碰计费链路） |
| `tenant_memberships` / `tenant_invitations` | ♻️ 企业成员体系 | 保留并启用（新建 API） |
| `model_pricing.tenant_id` 租户级定价 | ❄️ 一期冻结 | 全平台统一定价；数据能力保留，不开放管理入口，不写入租户价格行；二期作为企业协议价启用 |
| `wallets.tenant_id` | ♻️ 演化参考 | 企业钱包采用独立表方案（见 4.4），不改 `wallets` 语义 |
| `tenant_domains` 表 | ❄️ 冻结 | 解析已不走 Host；表保留，管理入口移除 |
| `brand_config` / `runtime_config` / `settlement_config` | ❄️ 冻结 | 字段保留，管理入口移除 |
| `tenant_models` 选品 | ❄️ 冻结 | 全平台统一模型目录 |
| 管理端 `/api/admin/tenants` CRUD | ♻️ 改造 | 变为「企业客户审核管理」 |
| epay 易支付 | 🗑️ 切换后移除 | 见第 6 节 |

### 2.5 裁剪原则

第一阶段只「冻结入口、改语义」，不删表不删列——历史数据可迁移、可回退；
稳定运行一个阶段后再评估物理删除。术语对照：

| 产品术语 | 代码/数据层 |
|---|---|
| 企业 | `tenants` 记录（`user_type=enterprise` 的组织实体） |
| 企业成员 | `tenant_memberships` |
| 企业钱包 | `enterprise_wallets`（新建，见 4.4） |
| 个人用户 | `users.user_type=personal`，无 active membership |

## 3. 企业管理规划

### 3.1 目标用户旅程

```
注册个人账号 → 控制台「企业中心」发起企业创建（企业名称/信用代码/执照/联系方式）
  → 平台人工审核（admin 后台；状态机已存在：pending_review → active / rejected）
  → 审核通过：创建者成为 owner，自动生成企业共享钱包
  → owner/admin 邀请成员（邮件邀请令牌，tenant_invitations）
  → 成员接受邀请 → 其 API 调用从企业钱包扣款，受成员月度上限约束
  → 企业充值（共享钱包）→ 成员消费 → 企业用量/账单统一可见
```

一期为**纯人工审核**；「自动通过 + 低额度试用、超额再审」列入二期。

### 3.2 数据模型变更

存量表已满足大部分需要，新增/变更：

```sql
-- 成员月度消费上限（一期决策 #5）
ALTER TABLE tenant_memberships
    ADD COLUMN monthly_limit DECIMAL(18,6);   -- NULL = 不限；单位 元/自然月

-- 企业共享钱包（独立表，不动 wallets 语义）
CREATE TABLE enterprise_wallets (
    id         UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id  UUID NOT NULL UNIQUE REFERENCES tenants(id) ON DELETE CASCADE,
    balance    DECIMAL(18,6) NOT NULL DEFAULT 0,
    frozen     DECIMAL(18,6) NOT NULL DEFAULT 0,
    currency   VARCHAR(8) NOT NULL DEFAULT 'CNY',
    version    BIGINT NOT NULL DEFAULT 0,     -- 乐观锁，与 wallets 一致
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

企业充值/消费流水复用 `wallet_transactions` 结构（或以 `holder` 标记区分持有者），
入账幂等键沿用现有唯一约束纪律。

### 3.3 新增 API

**控制台侧**（`/api/console/enterprise`，按 membership 角色鉴权）：

| 接口 | 角色 | 说明 |
|---|---|---|
| `POST /enterprise` | 任意登录用户 | 发起企业创建 → `tenants(status=pending_review)` + owner membership |
| `GET /enterprise` | 成员 | 我的企业信息 + 审核状态 |
| `GET/PUT /enterprise/profile` | owner/admin | 企业资料维护 |
| `POST /enterprise/invitations` | owner/admin | 创建邀请（复用 `tenant_invitations`） |
| `GET /enterprise/invitations` | owner/admin | 邀请列表 / 撤销 |
| `POST /enterprise/invitations/accept` | 被邀请人 | 令牌校验 → 写 membership |
| `GET /enterprise/members` | owner/admin | 成员列表（角色、月度上限、消费汇总） |
| `PUT /enterprise/members/{id}/role` | owner | 角色变更 |
| `PUT /enterprise/members/{id}/limit` | owner/admin | 设置成员月度上限 |
| `DELETE /enterprise/members/{id}` | owner/admin | 移除成员 |
| `GET /enterprise/wallet` | owner/admin | 企业钱包余额/流水 |
| `POST /enterprise/wallet/topup` | owner/admin | 企业充值（走第 6 节支付流） |
| `GET /enterprise/usage` | owner/admin；member 仅自己 | 企业维度用量（`usage_logs` 按 `tenant_id` 已有索引） |
| `GET /enterprise/billing/statement` | owner/admin | 企业月度账单（GMT+8 自然月，对齐个人账单口径） |

**管理后台侧**：`/api/admin/tenants` 语义改造为企业客户管理，新增审核动作：

```
PUT /api/admin/tenants/{id}/review   body: {decision: approve|reject, reason}
```
写入 `tenants.status` 与 `status_reason`，进审计日志。

### 3.4 注册流改造

- `HandleRegister` 接受并保存 `user_type` 字段（当前硬编码 `personal`）；
  企业注册 = 先建个人账号，引导进入企业创建流（不做「注册即企业」，
  避免未审核账号持有企业能力）；
- **同步修复审计问题 B2（账外注资）**：注册赠送/邀请奖励一律走 `wallets.TopUp`
  带幂等键的流水写入，禁止裸 `INSERT wallets`。

### 3.5 企业共享钱包接入计费链路

计费链路改动点只有一个入口——网关钱包解析：

```
现在：FindByUser(userID, nil)                    → 个人钱包
改为：查 active membership
      ├─ 有 → 企业钱包（企业状态非 active 时 fail-closed 拒绝）
      └─ 无 → 个人钱包
```

其余链路不动：定价 `tenantID` 已传递、证据链 `usage_logs.tenant_id` 已落库、
对账框架天然覆盖。计费引擎面向 `wallet.Repository` 接口，个人/企业钱包共享
既有的 Reserve/Commit/Settle 乐观锁 + 幂等实现。

**成员月度上限执行链路**（对齐不变量 #2「上游调用前预留」）：

```
网关请求进入
  → 解析企业成员身份（现有 membership 解析）
  → 【新增】月度配额预检：本月已消费 ≥ monthly_limit
        → 拒绝（429，错误码 member_quota_exceeded，进证据日志）
  → 企业钱包预算预留 → 路由上游 → Settle
  → 【新增】结算成功后原子累加本月消费计数
```

- 消费计数：Redis 原子累加 `member_spend:{tenant}:{user}:{YYYYMM}`，GMT+8 自然月
  （与月度账单口径一致）；金额按微元（×10⁶）整数存储，避免浮点漂移；
- 降级：Redis 不可用 → 回退 DB 汇总（`charge_lines` 按 tenant+user+月，走已有索引）；
  两者皆不可用 → **fail-closed 拒绝**（延续「错误不能伪装成成功」纪律）；
- 与 API Key `monthly_limit` 的关系：两层独立生效，先触发者先拦截；
- 配额按 membership 生效与角色无关；owner 自身记录默认 `NULL`（不限），可自设。

**状态联动**：

- 成员退出（membership → `left`）：回退个人钱包计费；
- 企业 `suspended` / `terminated`：其全部成员调用 fail-closed 拒绝（402/403）。

### 3.6 前端

- **控制台**新增「企业中心」页面组：创建向导、审核状态、成员管理（含月度上限编辑）、
  邀请管理、企业钱包、企业用量/账单；成员本人可见「本月已用 / 上限」进度；
- **管理后台** `Tenants.tsx` 改造为企业审核管理：企业资料、审核动作、状态与理由；
  移除域名/品牌/结算配置入口。

## 4. 权限管理规划（动态 RBAC）

### 4.1 平台层：数据模型（新增迁移）

```sql
CREATE TABLE admin_roles (
    id          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    code        VARCHAR(64) NOT NULL UNIQUE,   -- super_admin / ops / ...
    name        VARCHAR(128) NOT NULL,
    description TEXT,
    is_builtin  BOOLEAN NOT NULL DEFAULT FALSE, -- 内置角色不可删除
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE admin_role_permissions (
    role_id    UUID NOT NULL REFERENCES admin_roles(id) ON DELETE CASCADE,
    permission VARCHAR(64) NOT NULL,           -- 如 "channels:write"
    PRIMARY KEY (role_id, permission)
);

ALTER TABLE users ADD COLUMN admin_role_id UUID REFERENCES admin_roles(id);
-- 存量迁移：创建内置超级管理员角色（全权限）→ users.role='admin' 者挂到该角色
```

### 4.2 核心原则：权限目录固定，角色自由组合

- **权限点是代码定义的固定目录**（权限点必须与实际路由一一对应，新增权限必然
  伴随代码变更），按模块分组：

```
models:read/write        providers:read/write     channels:read/write
tenants:read/review      users:read/write         payments:read/complete
reconciliation:read      audit:read               settings:read/write
redemption:read/write    subscriptions:read/write gateway:read
roles:read/write         system:read
```

- **角色是权限点的任意组合**，管理后台可自由创建/编辑/删除
  （如「财务主管」「渠道运营」「只读审计」）；
- 写入 `admin_role_permissions` 时对照代码目录校验，未知权限点拒绝，杜绝孤儿数据。

### 4.3 种子角色（可编辑、不可删除）

| 角色 | 权限 |
|---|---|
| 超级管理员 | 全部（`is_builtin`，防删除/防清空） |
| 运营 | models/providers/channels/gateway 读写 + users/tenants/audit 只读 |
| 财务 | payments 读+补单、reconciliation、subscriptions、users/tenants/audit 只读 |
| 客服 | users/tenants/payments/gateway 只读 |

种子只是起点，上线后一切以管理员配置为准（一期决策 #4：自主配置，不写死）。

### 4.4 中间件与一致性

- `AdminAuth()` 演化为 `RequirePerm("payments:complete")` 按路由标注；
- 权限解析：`user.admin_role_id → admin_role_permissions`。沿用现有
  「每请求重查用户」的正确性优先模式，权限同样每请求查库（管理端流量低；
  角色改动立即生效，无缓存失效问题）；
- `GET /api/admin/me/permissions` 供前端过滤菜单与按钮。

### 4.5 防锁死保护（必须实现）

- 内置超级管理员角色不可删除、不可移除其权限；
- 禁止对自己降权/改角色；系统至少保留一名超级管理员（最后一人不可降级）；
- 删除角色前校验无用户挂载；角色变更全量进审计日志（复用 `AuditAdminWrite`）。

### 4.6 新增 API 与前端

```
GET/POST       /api/admin/roles              列表 / 创建
GET/PUT/DELETE /api/admin/roles/{id}         详情 / 改权限 / 删除
GET            /api/admin/permissions        权限目录（分组，供勾选 UI）
PUT            /api/admin/users/{id}/role    给用户分配角色（替换现有 role 接口）
GET            /api/admin/me/permissions     当前用户权限（前端菜单过滤）
```

前端新增「角色管理」页（模块分组复选框）；用户管理页角色下拉改为动态角色列表；
全站管理菜单/按钮按 `me/permissions` 显隐。

### 4.7 企业层：三级角色语义

`membership.role` 数据已存在，权限语义定义如下（企业层角色固定，不做自定义）：

| 能力 | owner | admin | member |
|---|:-:|:-:|:-:|
| 企业资料/解散 | ✅ | 只读 | — |
| 成员邀请/移除/改角色 | ✅ | ✅（不可动 owner） | — |
| 设置成员月度上限 | ✅ | ✅ | — |
| 企业钱包充值/查看 | ✅ | ✅ | — |
| 企业全量用量 | ✅ | ✅ | 仅自己 |
| 创建 API Key | ✅ | ✅ | ✅（扣企业钱包） |

JWT 已携带 `user_type / tenant_id / tenant_role`（`generateLoginJWT` 已实现），
无需改令牌结构。

### 4.8 数据级隔离

企业用量/账单查询强制 `tenant_id = 请求者 membership.tenant_id`；
管理后台查询不受限但全量审计。

## 5. 支付自接规划（替换易支付）

### 5.1 一期范围（决策 #1）

- **一期**：支付宝 + 微信 Native 扫码支付、订单补偿、对账接入；
- **二期**：企业对公转账（线下打款 + 管理端核销充值）、退款能力。

### 5.2 复用资产（无需重写）

- `Gateway` 接口（`CreateOrder` / `VerifyNotify`）——原设计即为可替换；
- `payment_orders` 状态机（pending/paid/closed/refunded）+ `expires_at` 超时字段；
- 回调入账幂等（`wallet_transactions.idempotency_key = order_no`）；
- 管理端手工补单（`AdminComplete`）。

### 5.3 新建内容

| 项 | 方案 |
|---|---|
| 支付宝适配器 | `smartwalle/alipay/v3` 升为直接依赖；PC 网站支付 / 当面付扫码 |
| 微信支付适配器 | `wechatpay-apiv3/wechatpay-go` 升为直接依赖；Native 扫码支付 |
| 回调路由 | `POST /api/payment/notify/alipay`、`/wechatpay`（epay 路由保留至切换完成） |
| `Gateway` 接口扩展 | `QueryOrder()` 主动查单（回调丢失补偿）；`Refund()` 二期 |
| 订单补偿 Worker | 周期轮询 `pending` 且临近过期订单 → 主动查单 → 关单或入账；挂现有 `cmd/worker` |
| 密钥管理 | 一期环境变量（商户号/证书路径/私钥）；二期入系统设置并以 `ENCRYPTION_KEY` 加密 |
| 对账 | 接入现有对账框架：支付账单文件 ↔ `payment_orders` 差异（对齐 L3 模式） |
| 企业充值 | 订单增加持有者维度（个人/企业），入账路由到对应钱包 |

### 5.4 安全基线

回调必做：签名验证 → 金额核对（`decimal` 逐分比对）→ 订单状态幂等 →
原始报文存 `notify_raw`。生产校验沿用 `config.validate` fail-fast 模式
（未配齐支付证书拒绝启动）。回调路由不挂鉴权中间件但强制 IP 白名单可选配置。

### 5.5 切换步骤

```
1. 新适配器开发 + 沙箱联调（支付宝/微信均提供沙箱）
2. 系统设置渠道开关，epay 保留兜底
3. 生产小额真实验证（1 分钱订单全链路：下单→回调→入账→对账）
4. 关闭 epay 入口 → 移除 go-epay 依赖与 handler、回调路由
```

## 6. ai-nuxt 落地页接口规划

### 6.1 定位与边界

**纯营销站，无认证状态**。登录/注册按钮跳转控制台站点（不在落地页做登录——
避免跨域 httpOnly Cookie 问题，边界最干净）。

### 6.2 架构：Nitro 服务端代理 + 缓存

```
浏览器 → ai-nuxt（Nuxt SSR/预渲染）
           └─ server/api/* → 后端 /api/public/*（服务端代理）
                               ├─ 隐藏后端真实地址
                               ├─ 数据结构转换适配前端组件
                               └─ 内存缓存 TTL 5~15 分钟（定价低频变更）
```

现有 `server/api/*.get.ts` 三个返回静态 JSON 的路由，改造为代理真实后端。

### 6.3 接口清单

| 落地页需求 | 后端接口 | 现状 |
|---|---|---|
| 定价页模型/价格（分组、峰谷价） | `GET /api/public/pricing` | ✅ 已存在（含 `models_public_visible` 开关），字段不足处增量扩展 |
| 站点品牌/公告/页脚 | `GET /api/public/site` | ✅ 已存在 |
| 价格排行 | `GET /api/public/rankings` | ✅ 已存在 |
| 平台运行数据（可选展示） | `GET /api/public/stats` | ✅ 已存在 |
| 模型健康状态页（如需） | 新增 `GET /api/public/models/status`（聚合健康数据，脱敏） | 🆕 按需 |

**要点**：落地页不新增认证接口、不碰 `/api/console`；公开接口已有 IP 限流，
代理层加缓存即可抗流量。

### 6.4 前置动作

- 🔴 **ai-nuxt 先纳入 git**（当前无版本控制，代码裸奔）；
- `data/pricing.json` 静态快照退役 → 接口数据 + 构建期兜底快照。
