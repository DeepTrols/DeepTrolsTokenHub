## 3. 背景与目标

### 3.1 业务背景

很多团队做 AI Token 聚合平台，第一反应是"接一个模型代理，暴露 `/v1/chat/completions`，把请求转给上游"。这能很快调通接口，但**还不是一个能收费上线的平台**。

真正决定系统能否对外售卖的，不是"请求能不能转发"，而是四件事：

- **控制面**：谁在调用？属于哪个租户？能用哪些模型？能花多少钱？
- **执行面**：这次请求走哪个上游？失败后能否 fallback？路由是否可回滚？
- **资金面**：请求前有没有锁住预算？请求后有没有准确落账？账单能不能解释？
- **证据面**：出问题后能否按 `request_id` 查清楚？新能力上线前有无 smoke、canary 与对账证据？

"能调通"离"能收费"很远。客户会问：我的 Key 为什么被扣这笔钱？同一请求重试两次为什么产生两笔费用？流式中断算成功还是失败？cache / reasoning / image token 分别怎么计费？OEM 流量为什么走了共享上游而不是我的专属池？平台也要问：余额不足时能否保证请求不打到上游？上游账单和 usage log 对不上以谁为准？LiteLLM spend log 能否直接当客户账单？

**结论**：AI Token 聚合平台不是反向代理，而是围绕模型调用构建的计费、风控、对账和运营系统。

### 3.2 产品愿景

> 成为应用与模型供应商之间的**推理控制层**：为开发者提供统一接入、模型选择与生产可靠性；为供应商提供生产流量、曝光与自动结算；平台掌握标准化、匹配、路由与交易证据。

### 3.3 产品目标（SMART）

| 目标 | 量化指标 | 时限 |
|------|---------|------|
| 形成可收费的交易闭环 | 统一 API + 模型目录 + 余额 + 调用记录 100% 跑通 | 一期 |
| 每笔请求可解释 | 100% 收费请求具备 usage log + charge line + 路由证据 | 一期 |
| 并发预算安全 | 高并发下钱包透支率为 0（预算预留前置于上游调用） | 一期 |
| 多渠道高可用 | 同模型支持 ≥2 个上游 channel，健康分驱动 fallback | 二期 |
| 可运营对账 | 四层对账（L0–L3）覆盖 100% 生产请求，差异可分类、可下钻 | 二期 |
| 企业/OEM 治理 | 支持租户状态机、模型选品、客户等级、配额池、独立账本 | 三期 |

### 3.4 市场参照（OpenRouter 案例分析要点）

OpenRouter（2026 年估值约 13 亿美元）的演进顺序值得借鉴，其护城河不是模型数量，而是逐步形成的六类能力：

1. **开发者分发** × 2. **供应商网络** × 3. **流量调度** × 4. **交易证据** × 5. **真实数据** × 6. **组织治理**
2. 演进主线：统一交易闭环 → 多供应商路由 → BYOK/客户资产 → Usage 与配置可运营 → 质量感知路由 → 企业治理 → 多模态复用底座 → Agent 运行基础设施。
3. 关键产品命题：统一接口只是获客手段（易复制）；真实请求性能数据 + 路由质量 + 交易信任才是壁垒。
4. 对自建平台的启示（迭代清单）：先闭合交易 → 再收口执行 → 补齐证据 → 开放客户资产 → 配置脱离代码 → 数据驱动路由 → 企业治理 → 扩展运行时 → 增长入口 → 公开市场数据。

### 3.5 用户角色矩阵

| 角色 | 核心诉求 | 痛点 |
|------|---------|------|
| **个人开发者 / 直客** | 一个 Key 调通多模型，价格透明 | 不同供应商 SDK 接入成本高；账单看不懂 |
| **企业客户** | 组织级预算、模型白名单、审计、SSO | 无法按团队/项目管控成本与权限 |
| **OEM 渠道商（Owner）** | 独立选品、定价、客户等级、配额、结算 | 不能把平台目录默认全开放；不能串价 |
| **平台运营 / Admin** | 租户治理、渠道健康、发布门禁 | 不清楚请求归属与成本归因 |
| **财务 / 对账人员** | 每笔收费可解释、可复核、可追责 | 上游账单与客户账单对不上 |
| **终端应用 / AI 编程工具** | Claude Code、Codex 等经兼容入口接入 | 配置复杂、易 401/404 |

## 4. 产品策略与价值主张

### 4.1 四层架构作为产品边界（核心策略）

平台必须同时具备以下四层，缺一层难以进入公开收费状态：

```
┌──────────────────────────────────────────────┐
│ 控制面 Control Plane │ API Key / HMAC / 租户隔离 / 模型目录 / 限额
├──────────────────────────────────────────────┤
│ 执行面 Execution Plane │ LiteLLM / Provider Adapter / 路由 / Fallback
├──────────────────────────────────────────────┤
│ 资金面 Money Plane │ Usage Log / Charge Line / 钱包 / 配额 / 价格快照
├──────────────────────────────────────────────┤
│ 证据面 Evidence Plane │ Raw Usage / Provider Cost / Invoice / Release Evidence
└──────────────────────────────────────────────┘
```

### 4.2 价值主张（按细分市场）

| 细分市场 | 现状（Before） | 解决方案（How） | 改变后（After） | 替代方案 |
|---------|--------------|---------------|----------------|---------|
| 个人开发者 | 每接一个模型写一套 SDK | 统一 OpenAI-compatible API + 一个 Key | 几行配置切换模型 | 各供应商官方 SDK |
| 企业 | 账号级余额，无项目隔离 | Workspace 级预算/白名单/审计 | 按团队治理成本与权限 | 自建网关 |
| OEM 渠道商 | 只有 tenant_id 字段 | 4 角色 + 选品 + 客户等级 + 配额池 | 独立经营下游客户 | 白标前端 |
| 平台方 | 上游账单即客户账单 | 自有 usage log / charge line | 每笔费用可解释、可审计 | 通用网关（NewAPI 等） |

### 4.3 竞品/工具边界决策（来自架构抉择）

| 工具 | 定位 | 平台使用方式 |
|------|------|------------|
| **NewAPI** | 通用 AI 网关与管理面板 | 仅作参考或轻量阶段工具，**不承担核心控制面** |
| **LiteLLM** | 多 provider 执行代理 | 平台控制面之下的**主要执行代理**（spend 仅作证据） |
| **自研原生 Adapter** | 特定 provider 原生能力接入 | 处理 Gemini 图片、Doubao Seedance 视频等原生语义 |
| **自研平台控制面** | 用户/租户/钱包/OEM/账本/审计 | 必须自研，不交给代理层 |

**核心原则**：工具可以替你转发请求，但不能替你承担客户账本和商业责任。

## 5. 范围定义

### 5.1 包含范围（In Scope）

- 一条能收费的 OpenAI-compatible 请求链路（身份→预算→路由→执行→计量→落账→证据）
- 计费引擎：定价、折扣、钱包、账本四层（配额体系已按 2026-08-25 移除）
- OAuth/OEM 体系：租户生命周期、模型选品、租户级定价、账本分层（企业/团队、客户等级、配额池已按 2026-08-25 收敛移除）
- 后端架构：模块化单体 + API/Worker 运行角色 + LLM 渠道高可用（channel / 共享池 / 独享池 / Route Policy / 负载均衡 / 健康治理）
- 对账系统：四层对账（L0–L3）+ 差异分类 + 复核流程
- 控制台：API Key 6 边界、调用日志、用量统计、钱包账单、模型广场、Playground、文档中心、安全设置
- 接口设计：16 个对外接口（同步/流式/异步视频）+ 三类协议鉴权 + 发布门禁

### 5.2 不包含范围（Out of Scope，本期）

- 自研基础大模型训练
- 通用微服务拆分（待组织边界成熟后）
- OEM 代管 API Key（高风险，MVP 隐藏，待权限/审计齐备再开）
- Fine-tuning、Vector Stores、Realtime、Rerank、Moderations 等非主链能力（需单独设计）
- OpenAI legacy `/v1/completions`、`/v1/batches`、`/v1/files` 等兼容接口

### 5.3 MVP 边界（MoSCoW）

| 类别 | 内容 |
|------|------|
| **Must（必须有）** | 控制面鉴权与租户隔离；预算预留前置于上游；usage log + charge line；OpenAI 兼容直连执行（渠道实例 base_url；内置 LiteLLM 已于 2026-08-19 移除）；基础定价与钱包实扣；调用日志与账单；非流式/流式主链；对账 L0/L1 |
| **Should（应该有）** | 多渠道 + 健康分 fallback；OEM 租户与模型选品（4 角色已收敛为单一开发者账号）；对账 L2/L3 差异分类；用量统计与模型广场；Playground 上线前验证；HMAC 验签（仅 webhook 用途） |
| **Could（可以有）** | /v1beta Gemini 原生端点；质量感知路由；多币种/FX；BYOK；视频下载与 Seedance 回调 |
| **Won't（本期不做）** | OEM 代管 Key；微服务拆分；Agent 编排（Advisor/Fusion/Subagent/MCP）；公开市场数据报告 |

| US-07 | 平台 Admin | 作为运营，我想用状态机管理租户生命周期，以便控制分销风险 | 租户治理 | 1. pending→active→suspended→terminated 显式流转；2. 有审计 |
| US-08 | 财务/对账 | 作为对账人员，我想按差异类型下钻请求，以便复核而非误改钱包 | 对账可运营 | 1. L0–L3 四层；2. 差异可分类；3. 资金动作走复核 |
| US-09 | 终端应用 | 作为 Claude Code/Codex 用户，我想经兼容入口接入，以便复用现有工具 | 低迁移成本 | 1. Anthropic/OpenAI-compatible 入口可用；2. 后台可见调用 |
| US-10 | 平台方 | 作为平台，我想在请求前锁预算，以便避免上游成本透支 | 资金安全 | 1. 预留前置于上游调用；2. 并发不超扣 |

### 6.2 关键流程（能收费的请求链路，13 步抽象为 4 阶段）

```
入口收口（谁在调用，能不能调用）
  → 鉴权、租户、限流、请求身份(api_key_id/user_id/tenant_id/request_id/request_type)
路由决策（这次请求怎么执行）
  → 模型解析 → 租户池 → 共享池 → Channel 选择（权重/健康/并发）
执行转发（上游调用如何完成）
  → 非流式：完整响应解析；流式：首 chunk 前可切换，之后不切，尾部 drain usage
资金证据（怎么收费，怎么解释）
  → usage → 价格 → usage log → charge lines → 钱包/配额/Key spend 提交 → 证据
```

**5 个不可破坏的不变量**：
1. `request_id` 不是全局唯一账务身份（需 `tenant+user+key+type+request_id`）
2. 预算预留必须发生在上游调用前
3. 路由结果必须进入证据链
4. `usage` 来源必须显式标记（upstream / final chunk / estimated）
5. 流式错误不能伪装成正常成功

## 7. 详细功能说明

### 7.1 网关与可收费请求链路

**功能描述**：所有对外模型调用统一收口到 OpenAI-compatible 网关，完成身份、预算、路由、执行、计量、落账、证据留存。

| 子功能 | 前置条件 | 主流程 | 异常流程 | 后置条件 |
|--------|---------|--------|---------|---------|
| 入口收口 | 请求到达 | 解析 api_key_id/user_id/tenant_id/request_id/request_type；校验状态/硬额度/模型白名单/来源 IP/HMAC 签名 | Key 不存在/过期/超限→401/403；HMAC 重放→拒绝 | 稳定请求身份写入上下文 |
| 路由决策 | 模型在目录 active | 先租户绑定池，再共享池；按健康分/并发/权重选择 channel | public model 非 active 或租户无权→fail-closed 拒绝 | channel/instance/route policy 写入证据 |
| 执行转发（非流式） | channel 选中 | 转发实例执行；解析 usage；恢复对外模型名；计算价格；写 usage log + charge line | 上游失败→按策略处理，不伪装成功 | 返回 OpenAI-compatible 响应 |
| 执行转发（流式） | 首个 chunk 前 | 首 chunk 前可处理失败；首 chunk 后不切 provider；要求尾部 usage | 客户端断开→停止转发但 drain 上游流拿 usage | final usage/estimated/disconnect 入账 |
| 资金证据 | usage 解析完成 | estimated→cost→reserve→execute→usage parse→price→usage log→charge lines→commit | 计费提交失败→额度/钱包补偿或转 reconcile | metrics + evidence 落地 |

**验收要点**：
- 每个请求具备稳定 `api_key_id/user_id/tenant_id`
- 租户边界 fail-closed（未知 Host 不回落平台）
- 预算控制：上游调用前完成钱包/配额/Key spend 预留
- 路由证据：可记录 channel/instance/provider route/route policy
- 错误语义：上游错误/客户端断开/超时 不伪装成正常成功

### 7.2 计费引擎

**功能描述**：从模型定价、租户/OEM 选品、用户等级折扣，到配额优先、钱包实扣、usage log 与 charge line 的完整链路。

**五层拆分**：

| 层 | 回答的问题 | 关键规则 |
|----|-----------|---------|
| 定价 | 客户侧折前价 | 客户价与上游成本两条线；支持 request type/计量单位/参数的条件计价 |
| 折扣 | 钱包部分优惠多少 | 用户等级≠直接改模型价；命中优先级最高一条，生成折扣快照；套餐额度不二次打折 |
| 配额 | 哪些用量由套餐/租户额度覆盖 | 优先消耗套餐额度 |
| 钱包 | 现金余额实扣，幂等 | decimal 不用 float；预留→实扣→多退少补 |
| 账本 | 事后凭什么对账 | usage log + charge line + wallet tx + quota ledger + API Key spend + provider evidence |

**完整扣费顺序（不可乱）**：
1. 判断可用计费模型（租户未上架/价格缺失→拒绝，不默认 0 元）
2. 计算折前客户价（list_cost）
3. quota 覆盖可覆盖部分
4. 对 wallet 部分应用 PAYG 折扣
5. wallet 实扣 + 账本落地

**金额公式示例**：
```
list_cost = 折前客户价
wallet_before_discount = 配额覆盖后需钱包支付部分
discount = wallet_before_discount * (1 - discount_rate)
final_cost = list_cost - discount
wallet_cost = wallet_before_discount - discount
```

**账本六类记录**：usage log（请求级）、charge line（维度级）、wallet transaction、quota ledger、API Key spend、provider evidence。`sum(charge lines) == usage log cost`。

**验收要点**：
- 模型基础价必须有可用客户价
- 支持条件定价（request type/计量单位/参数）
- OEM 模型选品与价格独立可控
- 关闭 PAYG 时只允许 quota 覆盖
- 平台直客等级与 OEM 客户等级分开解析
- 请求前预估最大用量 + 上游前占用预算
- 钱包实扣有幂等 transaction；失败可补偿
- 价格快照保存 source/version/FX/渠道成本
- 客户价低于上游成本时拒绝放量（毛利保护）

### 7.3 OEM / 租户体系

**功能描述**：把平台能力拆成租户化的开通、选品、定价、客户、资金、配额、账本、权限边界。

**4 个角色**：平台 Admin / OEM Owner / OEM 下游客户 / Gateway+Billing（系统）。

**核心能力域**：

| 能力域 | 需求 | 验收 |
|--------|------|------|
| 租户生命周期 | 状态机：create→pending_review→approve→active→suspend→terminated | 创建即绑 Owner、初始化配置、写审计；拒绝/终止有原因 |
| 租户识别 | Host 优先；受信 Header 备选；未知 Host fail-closed | 域名命中后不允许 Header 覆盖；缓存只是热路径 |
| 多租户隔离 | 显式 tenant scope（Repository 显式收 tenantID） | 平台直客 `tenant_id IS NULL`，OEM `tenant_id=?`，Admin 专用 scope-all |
| 模型选品 | 平台目录 left join 租户配置 | PAYG 价格不完整→拒绝调用；不出现"能调用但免费打上游" |
| 客户等级 | OEM 独立等级（`ai_discount_rate`），不复用平台等级 | ❌ 已取消（2026-08-25 OEM 进阶不再实施） |
| 客户管理 | 列表/封禁/调级/代充值 带租户边界 | ❌ 已收敛（企业/团队体系 2026-08-25 移除；租户基础能力保留） |
| 钱包 | 余额 + 流水 + 乐观锁 | 余额变更统一走流水；订阅/签到/兑换码入账 |
| API Key 代管 | 当前隐藏，不半开放 | MVP 客户自管；明文仅创建时返回；不提供 OEM 代管入口 |
| 账本可见性 | OEM 看经营数据，平台保留底层账本 | OEM 不看平台供应商凭证/全局上游成本 |

**验收要点**：不把 OEM 做成白标前端；公开请求不靠参数传 tenant_id；平台模型不默认给所有 OEM；余额变更统一走流水；OEM 看板不暴露平台成本。

### 7.4 后端架构与 LLM 渠道高可用

**功能描述**：用模块化单体 + API/Worker 运行角色承载业务复杂度；把 LLM 渠道高可用独立建模为转发实例、channel、池、Route Policy、负载与健康的治理系统。

**后端边界**：
- **API 进程**：同步请求、门禁、预算、路由选择、响应收口（不做后台扫描/跨 channel 连环重试）
- **Worker 进程**：定时/异步/补偿/对账/健康检查（不阻塞用户请求；共享领域模型与 repository 契约）
- 模块化单体（handler/service/repository/model 分层），service interface / repository interface 为未来微服务铺垫
- 异步计费使用 durable outbox（API 写 event → Worker 扣款/落账，幂等）

**LLM 渠道边界**：

| 对象 | 职责 | 不做什么 |
|------|------|---------|
| 转发实例 | 协议转发、上游适配、实例内 retry/fallback | 不判断钱包/折扣/OEM 分账；不写客户 usage log |
| channel | 平台侧调度/隔离/成本归因单元 | 不保存上游凭证 |
| Route Policy | 候选池、租户/用户/等级策略、fallback | 不直接调上游 |
| Worker | 健康/探活/异步账单/对账 | 不阻塞请求 |

**渠道高可用规则**：
- 共享池 / 租户独享池 / 混合池；独享池不可用时是否回共享池**由策略显式决定**
- 路由：`RouteContext + Route Policy`（tenant/user/level/model/request_type），fallback_policy 显式（disabled / tenant_default / shared_allowed / next_policy）
- 默认路由：先租户绑定池 → 再共享池；候选过滤（active/health≥50/并发/实例 active/非 pending setup）
- 负载均衡：weighted least-load（基于 Redis 实时 current_load，DB 仅展示副本）
- 健康监测：Worker 每 60s 算 health_score；<30 持续 3 分钟自动降级；>70 持续 5 分钟恢复；Admin 手动禁用不自动恢复
- 平台层不跨 channel 连环重试（provider retry 属转发执行层内部）

**验收要点**：API/Worker 同代码不同运行角色；模块间经 service interface；Worker 任务有业务唯一键+幂等；channel 承载租户/权重/并发/健康/成本；同模型可配多 channel；fallback 显式；health_score 由 Worker 更新；DB current_load 不做实时路由。

### 7.5 对账系统

**功能描述**：把四类事实（下游调用、平台落账、上游转发、供应商账单）分开保存，用请求身份串起来，形成可解释、可复核、可追责的证据链。

**四层对账模型**：

| 层 | 看什么 | 回答的问题 |
|----|--------|-----------|
| L0 客户请求账本 | 每一条客户请求的用量与费用 | 客户为什么扣费/失败 |
| L1 上游转发证据 | 转发实例访问上游的每条记录 | 是否真的打到上游、拿到 usage 没 |
| L2 平台内部对账 | L0 与 L1 逐请求核对 | 客户账与转发证据能否互释 |
| L3 上游账单对账 | L1 与供应商官方账单核对 | 转发消耗能否被供应商账单解释 |

**差异分类（4 类高频）**：
1. L0 成功、L1 缺证据 → 标记缺失，生成复核项，修证据链（不自动退款）
2. L0 失败、L1 也失败 → 可解释失败，不收费
3. **L0 失败、L1 后来成功** → 最危险，进财务复核（不静默补扣）
4. L0/L1 总量一致但明细维度不一致 → 补维度映射与报表说明（不动钱包）

**Usage 归一化**：平台客户账本维度 input/output/cache read/cache write/reasoning/image/audio；上游原始字段保留用于对账。跨协议（OpenAI ↔ Anthropic ↔ Gemini）必须同时保存入口事实与上游事实。

**核心产品原则**：**对账任务只能发现差异，不能直接改钱包**。资金动作必须进入复核流程（分配/备注/调整/豁免/关闭/重开 + 审计）。

**产品经理验收清单**：日级汇总、请求级下钻、差异分类、跨协议对照、客户账本（仅客户价）、运营对账证据、复核流程、审计记录。

### 7.6 控制台

**功能描述**：让客户从接入、上线、控费、排障到安全治理自助闭环。API Key 是企业级最小治理单元。

**API Key 6 边界**：身份 / 模型 / 来源 / 预算 / 状态 / 证据。

| 能力 | 需求 | 验收 |
|------|------|------|
| 创建 Key | 明文仅展示一次；创建即配限额/模型白名单/来源白名单 | 关闭后列表仅脱敏；提示存入密码管理器 |
| Key 状态 | 激活/停用/撤销/超限 区分 | 列表可筛选；展示最后使用时间、7 日活跃 |
| 模型白名单 | 空白名单=允许全部；非空白名单=仅指定 | 与 Playground 联动过滤可用 Key |
| 来源白名单 | 全局默认 + 单 Key 覆盖，IP/CIDR 一行一条 | 两层配置 |
| 消费限额 | 累计/周/月上限 + 超限策略（停止/警告） | 列表展示预算进度 |
| Key 不孤立 | 跳转调用日志/用量统计/账单 | 按 Key 反查请求、看趋势、解释成本 |

**其他控制台能力**：
- 调用日志：客户侧账本入口，支持按 Key/请求 ID/模型/状态/类型/协议筛选；可展开计费明细
- 用量统计：采购看趋势（钱/模型结构/cache 节省），技术看异常（错误率/流量异常）
- 钱包账单：可用余额/冻结/交易流水/月账单；关联 AI 用量；余额预警
- 模型广场：放在 Key 后面；展示类别/厂商/上下文/价格维度/套餐余量/折扣
- 模型详情：把价格讲透（input/output/cache read/write/image/video/audio/TTS/pricing rule/quota-wallet）
- Playground：上线前验证台，用真实 Key/权限/余额；覆盖对话/向量/图片/视频/语音/TTS
- 文档中心：与控制台互相跳转（快速入门/认证/计费/错误码/示例）
- 安全设置：MFA、登录记录、Key 禁用/删除/限模型/限来源/限额

**验收要点**：客户侧不暴露供应商成本与执行侧调度信息；页面按任务拆、对象按事实拆、关键页面互相串联。

### 7.7 接口设计

**功能描述**：16 个对外接口构成可复用接口设计，模型发布、请求路由、不同模态计费、同步/流式/异步一致。

**关键原则**：
1. 16 条路由不是一条转发链；内部 `request_type` 统一命名（语音合成建议仅 `tts`）
2. 模型可调用需同时满足：active 目录 ∩ 租户启用与价格 ∩ API Key 白名单 ∩ 活跃渠道/路由 ∩ 能力门禁 ∩ 余额/额度
3. 每次请求只选一个逻辑 Channel；Provider 级 retry/fallback 在转发实例边界
4. 通用模型走动态目录；图片/音频/视频需额外能力契约与发布门禁
5. 原生协议按能力分阶段发布（如 Gemini 图片只开放文本提示生成图片，拒绝其他）
6. 异步视频必须设计创建/回调/轮询/交付/取消/终态结算

**16 接口概览（按模态）**：

| 类别 | 接口 | 上游 | 计费/幂等要点 |
|------|------|------|--------------|
| 文本 | `/v1/chat/completions`、`/v1/responses`、`/v1/messages`、`/v1/messages/count_tokens` | 转发实例 | token/cache 5m/1h/output；非流式可回放，流式只防重复；count_tokens 免费预估不扣费 |
| 目录 | `GET /v1/models` | 不调 Provider | 不计费；仅租户+Key 的模型发现快照 |
| 向量 | `/v1/embeddings` | 转发实例 | 按 input token；入口拒绝空 model/input/超大批次 |
| 图片 | `/v1/images/generations`、`/v1/images/edits` | 转发实例 / Gemini | 按最终图片数；同步可回放，流式只防重复 |
| 音频 | `/v1/audio/transcriptions`、`/v1/audio/speech` | 转发实例 | 转录按秒（无 duration 按文件大小估算）；TTS 按字符，先计费提交再交音频流 |
| 视频 | `/v1/videos/generations` + 查询/内容/取消/Provider callback | Doubao Seedance 原生 | 创建时预占，成功终态结算，失败/过期由 finalizer 释放；callback nonce 防重放 |
| Gemini | `/v1beta/models/{model}:generateContent` | Google Direct 或转发实例 | 按实际图片数；仅两个图片模型；非流式可回放 |

**三类协议鉴权**：OpenAI-compatible（Bearer/HMAC）、Anthropic Messages（+`x-api-key`）、Gemini Native（+`x-goog-api-key`）；Seedance callback 校验 task token/时间戳/HMAC/nonce；Console 用 JWT + owned `api_key_id`，浏览器不接触 Key 明文。Handler 拒绝客户覆盖 `api_key/headers/base_url` 等顶层字段。

**发布门禁（"模型已支持"证据顺序，强度从低到高）**：
1. 静态文档/示例配置 → 2. 接口与服务代码 → 3. 部署环境数据（目录/租户模型/Channel/价格/Key 权限） → 4. 指定租户模型列表响应 → 5. 带真实凭证的 smoke → 6. 完整账单与对账证据（请求日志/usage/费用明细/路由快照/上游账单逐项对应）。

**上线前检查边界（高优先）**：写接口与 Provider callback 的安全中间件顺序；Seedance callback nonce 防重放；取消异步任务必须进 finalizer 释放 reservation；契约/Validator/模型详情一致；Responses 图片组合计费；GLM-5.2 经 Anthropic 的 cache usage 验证。

## 8. 非功能需求

### 8.1 性能
- 路由选择毫秒级（基于 Redis 实时 current_load，非 DB 字段）
- 预算预留前置于上游调用，并发不超扣（INCR 后校验 + Lua 释放 + TTL）
- 异步计费用 durable outbox，不阻塞请求线程

### 8.2 安全
- API Key：明文仅创建时返回；脱敏列表；HMAC（method/path/body SHA256/±300s 时间窗/Redis nonce 防重放）
- 租户识别 fail-closed（未知 Host 不回落平台；域名命中后不允许 Header 覆盖）
- 凭证隔离：上游 key 仅来自平台加密配置；拒绝客户覆盖 base_url/api_key/headers/callback_url
- 账户安全：MFA、登录记录、Key 禁用/删除/限模型/限来源/限额
- 对账任务不直接改钱包；资金动作走复核 + 审计

### 8.3 可靠性
- 5 个不变量不可破坏（见 6.2）
- 流式客户端断开仍 drain 上游流拿 usage
- 渠道健康：health_score 自动降级/恢复；Admin 禁用不自动恢复
- 独享池故障是否回共享池由策略显式决定
- outbox durable，Worker 幂等（重复 claim 不重复扣费）

### 8.4 兼容性
- OpenAI-compatible 为主入口（降低迁移成本）；支持 Anthropic Messages、Gemini Native
- Claude Code / Codex 经兼容入口接入（附录配置手册）
- 跨协议 usage 归一化（OpenAI ↔ Anthropic ↔ Gemini）

### 8.5 合规与精度
- 金额使用 decimal，禁止 float（避免对账误差）
- 多币种保存汇率来源与版本（旧账不被未来汇率重解释）
- 客户账本与平台底层账本分层展示（OEM 不看平台成本）

## 10. 风险评估与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 预算预留缺失导致上游成本透支 | 中 | 高 | 预留严格前置于上游调用；并发 INCR 校验 |
| 流式中断伪装成功，账务错乱 | 中 | 高 | 首 chunk 后不切 provider；drain 上游拿 final usage；错误语义不伪装 |

| 代充值对不上账 | 低 | 高 | 同租户钱包转账 + 事务 + 流水 + 审计 |
| 对账任务误改钱包（资金事故） | 中 | 极高 | 对账仅发现差异；资金动作走复核流程 |
| 独享池故障偷偷回共享池破坏 SLA | 低 | 中 | fallback_policy 显式，不允许隐式兜底 |
| 渠道高可用靠错层（微服务解决上游不稳定） | 中 | 中 | LLM 渠道高可用独立建模，不靠业务微服务 |
| 新模型上线无证据包就放量 | 中 | 高 | 发布门禁 6 级证据；smoke/canary/route snapshot |
| 上游依赖/中心化故障（参考 OpenRouter 2026-02 缓存故障） | 低 | 高 | 断路器、受控缓存回填、准确错误码、公开复盘 |

## 12. 上线门禁与验收清单（发布证据包）

新模型/新能力公开收费前，必须能回答"当时为什么认为可以收费上线"：

- [ ] 非流式请求能返回正确 usage
- [ ] 流式请求能拿到 final usage，异常时不伪装正常结束
- [ ] cache / reasoning / image / audio 等计费维度被正确识别
- [ ] usage log 可查；charge line 可查；LiteLLM raw usage / provider evidence 可查
- [ ] route snapshot 说明当时模型/provider/价格版本
- [ ] 有 smoke / canary / provider matrix / 价格与账单验证
- [ ] OEM 租户入口、模型、账务隔离已验证
- [ ] 对账 L0–L3 可覆盖该能力；差异分类与复核流程可用

**分阶段验收门槛（参考 OpenRouter 迭代清单）**：
