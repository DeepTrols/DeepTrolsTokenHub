# P0.5 Production Safety Gate

## Code Audit Before Task Creation

Existing:

- `internal/config/config.go` 已有生产 fail-fast，覆盖弱密钥、`COOKIE_SECURE`、`ADMIN_PASSWORD` 与 fake payment。
- `internal/handler/gateway/chat.go`、`endpoints.go`、`responses_via_chat.go` 等网关路径已在上游调用前执行钱包 reserve。
- `wallet.Repository` 已有 `Reserve/Commit/Settle/Release/TopUp/Spend/Transfer`，使用 decimal、行锁、乐观锁与幂等键。
- `internal/worker/reconciliation` 已能发现 L0-L3 差异；产品原则要求它只能发现差异，不能直接改钱包。
- `cmd/worker/main.go` 已对现有 worker 加 Redis lease。
- `docs/DEPLOYMENT.md` 记录了备份、恢复、迁移、灰度、回滚和多实例注意事项。

Partial:

- B5 少收路径仍存在：实际费用超过预留时，现有链路会把少收标记为 `undercharged`，但预留策略和 fallback 行为未被 P0.5 明确治理。
- B7 有备份命令，但缺少可恢复性基线和实际 restore drill 记录。
- B8 有部署手册，但缺少从空环境启动、迁移、探针、网关调用、对账的独立验收任务。
- `payment_orders.pay_url` schema/DTO 已存在，但当前创建订单未持久化 `pay_url`。
- Worker lease 有代码，但缺少基础观测。

Missing:

- 基于 `max_tokens` 的最大费用预留策略。
- `Settle` 失败 fallback 的少收可见性与复核入口约束。
- P0.5 级账务不变量与并发测试矩阵。
- 基础 billing metrics 与生产告警。
- 备份基线、恢复演练、干净环境部署验证。
- 生产安全门 Harness。

Risks:

- 不先治理 B5 就进入真实支付，会把少收问题带到收费链路。
- 未演练恢复与干净部署时，线上事故和新环境发布都不可验证。
- 订单支付链接不持久化会影响用户继续支付。
- Worker 无观测时，lease 失效或跳过只能靠人工看日志。

## Sprint Tasks

### TH-P05-01

Task ID: TH-P05-01
Title: B5 Reserve Maximum Charge Calculation
Phase: P0.5
Epic: Production Safety Gate
Type: Backend / Billing
Priority: P0
Dependencies: None

Objective:

Replace minimum/rough reserve for chat-like requests with a maximum-charge calculation derived from declared `max_tokens` and prompt estimate before any upstream call.

Current State:

The gateway reserves before upstream, but B5 remains because actual cost can exceed the reserved amount and later fallback commits only the reserved value.

Scope:

Implement the max-charge hold calculation for primary text inference paths and expose calculation reasons for tests.

Out of Scope:

Provider adapters, reconciliation review UI, enterprise wallet.

Implementation Notes:

Keep decimal arithmetic. When `max_tokens` is absent, use the existing safe estimate plus documented cap rules.

Acceptance Criteria:

- AC-01: Given `max_tokens=1000` and complete input/output pricing, reserve amount equals estimated input cost plus max output cost before upstream call.
- AC-02: Given missing output pricing, the request returns `pricing_incomplete` before upstream call and creates no reserve transaction.
- AC-03: Given `max_tokens` is absent, reserve amount follows the documented fallback cap and is never below the previous minimum hold.
- AC-04: Given streaming and non-streaming chat requests with the same pricing inputs, both use the same hold calculation.

Test Requirements:

- Unit: max-charge calculator table tests.
- Integration: gateway reserve amount is asserted before executor call.
- Regression: existing pricing-incomplete and wallet-missing cases remain covered.
- Failure Injection: missing pricing and malformed `max_tokens`.

Observability Requirements:

Emit hold calculation mode, pricing completeness, and reserve amount bucket without request body text.

Audit Requirements:

No audit row; reserve is captured by wallet ledger.

Migration / Rollback Requirements:

No migration. Rollback returns to prior reserve calculation and must keep B5 alert enabled.

Documentation Requirements:

Document max-charge formula and fallback cap in billing docs.

Risks:

Over-reserve can reject valid low-balance users. Formula must be visible and tested.

Global DoD applies.

### TH-P05-02

Task ID: TH-P05-02
Title: B5 Settle Fallback Visibility Correction
Phase: P0.5
Epic: Production Safety Gate
Type: Backend / Billing
Priority: P0
Dependencies: TH-P05-01

Objective:

Make actual-greater-than-reserve settle failures explicit, reconciliation-visible, and barred from any automatic wallet recoup path.

Current State:

The code records `undercharged` evidence when settle cannot charge actual cost beyond reserve, but P0.5 did not previously make this a first-class safety task.

Scope:

Pin settle fallback behavior, mark undercharge reason consistently, and ensure no reconciliation or worker path directly calls wallet debit for the difference.

Out of Scope:

Manual review UI, provider payment, enterprise wallet.

Implementation Notes:

If response has already been delivered, preserve ledger truth and emit review evidence; do not silently mutate original usage/evidence rows.

Acceptance Criteria:

- AC-01: Given final amount exceeds reserved amount and wallet has no additional available balance, the request records `undercharged=true` and the final ledger remains mathematically consistent.
- AC-02: Given the same request id is replayed, no additional wallet debit is created.
- AC-03: Given reconciliation later sees the undercharge flag, it creates or can create a diff/review input and does not call `Spend`, `TopUp`, `Adjust`, `Reserve`, or `Settle`.
- AC-04: Given normal final amount is less than or equal to reserve, settle completes without undercharge flag.

Test Requirements:

- Unit: settle fallback classifier.
- Integration: wallet ledger and usage evidence for over-reserve and under-reserve cases.
- Regression: stream and non-stream success paths stay billable.
- Failure Injection: settle DB failure and idempotent replay.

Observability Requirements:

Metric for undercharge fallback count by endpoint and model; log request id only.

Audit Requirements:

No automatic money audit row. Future manual adjustment audit is handled in P5 review tasks.

Migration / Rollback Requirements:

No migration. Rollback must keep undercharge metrics and reviews disabled rather than auto-debiting.

Documentation Requirements:

Document that undercharge differences enter review, not automatic wallet mutation.

Risks:

Incorrect fallback can either hide revenue leakage or overcharge customers. Tests must pin both sides.

### TH-P05-12

Task ID: TH-P05-12
Title: B5 Non-Chat And Multimodal Coverage Closure
Phase: P0.5
Epic: Production Safety Gate
Type: Safety / Billing
Priority: P0
Dependencies: TH-P05-01
Status: TODO

Objective:

Close the B5 coverage gaps (Batch 1 C-1/C-2/C-3) so every gateway endpoint
that can generate provider cost is classified into an explicit reserve
strategy, and no endpoint silently falls back to `minHoldAmount`.

Current State:

TH-P05-01 wired maximum-charge reserve into the four chat-shaped text paths.
The Batch 1 audit recorded three gaps: direct `/v1/responses` (polymorphic
input) and `/v1/completions` use empty estimators (C-1); embeddings/images/
STT/TTS/video silently fall back to `minHoldAmount` on pricer error (C-2);
chat multimodal content parts are not counted in the prompt estimate (C-3).

Scope:

Systematically inventory every gateway entry that can produce provider cost,
build an `Endpoint -> Pricing Unit -> Maximum Exposure -> Reserve Strategy`
matrix, and assign each endpoint one of exactly three strategies:
A. Maximum Charge Reserve, B. Safe Fixed Cap Reserve, C. Fail-Closed.

Out of Scope:

New pricing models, changing list prices, provider billing contracts. The
pricing unit for each endpoint is taken from the current Pricing Engine, not
invented here.

Implementation Notes:

A fourth strategy is forbidden: "cannot compute, so silently use
minHoldAmount" must not exist anywhere. Multimodal inputs that cannot be
reliably estimated must go to safe-cap or fail-closed, never under-estimated
as pure text.

Acceptance Criteria:

- AC-01: Every gateway endpoint that can produce provider cost appears in the
  B5 Coverage Matrix; no endpoint is left unclassified.
- AC-02: `/v1/responses` polymorphic input computes or safely estimates input
  cost and maximum output exposure; it must not degrade to an obviously
  insufficient minimum hold just because input is not chat messages.
- AC-03: `/v1/completions` must not silently use minimum hold because the
  prompt estimate is empty.
- AC-04: embeddings / images / STT / TTS / video each establish a reserve
  strategy from their real pricing unit (token / image / second / minute /
  generation / request) as defined by the current Pricing Engine.
- AC-05: If the Pricing Engine returns an error, a missing field, or cannot
  determine a safe maximum cost, the provider must not be called with only a
  `minHoldAmount` reserve; the architecture-permitted fail-closed path, or an
  explicitly-proven-safe fixed cap, must apply.
- AC-06: Chat multimodal content parts are included in the input cost
  estimate; any multimodal input that cannot be reliably estimated must go to
  safe-cap / fail-closed, not be under-estimated as pure text.
- AC-07: Every endpoint verifies the ordering Required Reserve -> Reserve
  Success -> Provider Call; Provider Call -> Reserve is forbidden.
- AC-08: Reserve amount is never negative, never uses float money arithmetic,
  never silently becomes 0 on parse anomaly, and never silently drops to
  `minHoldAmount` on pricing error.
- AC-09: Each endpoint type gains tests covering at least: normal pricing,
  pricing incomplete, pricing error, malformed request, maximum exposure, and
  provider-not-called-before-reserve.
- AC-10: A final B5 Coverage Matrix is produced stating
  Uncovered Provider-Cost Endpoint = 0; otherwise this task is not DONE.

Test Requirements:

- Unit: per-endpoint reserve strategy classifier and exposure estimator.
- Integration: reserve-before-provider ordering and fail-closed behavior.
- Regression: all existing chat / responses / claude / endpoint tests stay green.
- Failure Injection: pricing error, missing pricing field, malformed body.

Observability Requirements:

Hold calculation log line records endpoint, strategy, and reserve bucket; it
must not include request body text.

Audit Requirements:

No app audit row.

Migration / Rollback Requirements:

No migration. Rollback restores the prior per-endpoint reserve behavior while
keeping the coverage matrix documented.

Documentation Requirements:

Publish the B5 Coverage Matrix and per-endpoint pricing-error semantics.

Risks:

Under-reserving any provider-cost endpoint reopens the B5 undercharge hole;
over-reserving can reject low-balance users. Both sides must be pinned by tests.

Definition of Done:

Global DoD applies.
