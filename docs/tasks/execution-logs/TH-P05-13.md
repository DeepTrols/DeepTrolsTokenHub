## 2. Root Cause（精确同步关系，非"时序问题"）

修复前的 Case A 编排存在一个**仅由测试构造组成的循环等待**，且其
成立与否取决于哪个请求赢得 Reserve 竞速——这就是抛硬币式抖动的根源：

- 观察钱包 `p0503ObservedWallets.Reserve` 在互斥锁下计数 Reserve 尝试：
  第 1 次尝试直通（ungated），第 ≥2 次尝试阻塞在 `gateSecondReserve`
  通道上，直到主测试 `close(secondGate)`。
- mock executor 中，**首个进入者** `close(winnerExecuting)` 后阻塞在
  `proceed` 通道上（5s 墙钟守卫）。哪个请求先进入 executor，取决于谁
  赢得 Reserve 竞速。
- 主测试编排为：`<-winnerExecuting` → `close(secondGate)` →
  **`<-secondDone`** → `close(proceed)`。而 `secondDone` 被**硬连线**到
  goroutine #2（req2）的 handler 返回。

循环等待链（当 req2 赢得 Reserve 竞速时）：

```
main ──等待──> secondDone ──属于──> req2 的 handler
req2 ──阻塞在──> executor 内的 proceed 通道
proceed ──只有──> main 在收到 secondDone 之后才会 close
```

即 `main → secondDone(req2) → proceed → main` 的循环。req2 既是被等待
完成的一方，又是被 `proceed` 卡住的一方——只有 5s 墙钟守卫打破死锁，
报错形态固定为 `executor gate timed out — test orchestration deadlock`。
当 req1 赢得竞速时，`secondDone`（req2）恰好是败者、能正常返回，编排
碰巧成立——故通过率约等于抛硬币（Batch 4A 取证：基线失败率 4/6）。

**不是生产并发缺陷**：等待环中只有测试通道与 mock executor；生产
DB 路径（钱包冻结/扣减、账本、计费行）在两种竞速结果下都能走通，
失败运行中的资金断言同样全部成立。因此按指令判定为测试编排缺陷，
继续修复而非停报 "Production Concurrency Defect"。

## 4. Scope A — 确定性编排（仅测试文件）

新模型（全部在 `invariants_p0503_test.go` 内，生产代码零改动）：

1. **胜者 = Reserve 第 1 次尝试**（观察钱包直通），进入 provider 检查点，
   `enteredProvider` (`sync.Once`) `close(winnerAtProvider)` —— READY 信号；
   随后阻塞在 `proceed` 上等待 RELEASE。
2. **败者 = Reserve 第 2 次尝试**（被 `gateSecondReserve` 门控）。
3. 主测试编排（每步注释标明语义）：
   - `p0503WaitOrchestration(t, winnerAtProvider, ...)` —— 胜者已冻结 hold；
   - `close(secondGate)` —— 释放败者的门控 Reserve，令其对已冻结 hold 发起
     预留，必须被钱包/DB 安全拒绝（402 前置可用性检查 或 500 DB 级拒绝）；
   - `p0503WaitOrchestration(t, firstFinished, ...)` —— **构造性不变量**：
     胜者在 RELEASE 前不可能返回，所以首个返回的 handler 必为败者；
     `handlerReturned` (`sync.Once`) 由任一先返回的 handler 关闭
     `firstFinished`，等待的是角色而非固定 goroutine；
   - `close(proceed)` —— RELEASE，胜者完成 provider 调用并结算；`wg.Wait()`。
4. 超时仅为死锁守卫：`p0503OrchestrationGuard = 30s` 内未收到角色事件则
   `t.Fatalf` 指明断点；executor 内保留 5s 守卫（同样只防挂起）。

**保留的业务断言逐字不变**：恰好一个 200 + 一个 402/500；
`executeCalled == 1`；余额 = 注资 − 单次最终费用；frozen = 0；
2 条账本行（充值 + 一次预留转扣费）；1 条 charge 行；
`assertInvariants`（W1–W3、W11 账本-余额一致性）。

## 5. Scope B — 门禁脚本退出码完整性契约

动机：Batch 4B 发现 `go test | tail` 在测试失败时仍返回 0（管道退出码
被 tail 吞掉），门禁误报绿。

交付（最小契约，完整 harness 仍属 TH-P05-09）：

- `scripts/gate_command.sh`：`set -euo pipefail`；显式捕获被包装命令的

  `command > logfile 2>&1; status=$?; tail -n 80 logfile; exit $status`；

  `//go:build ignore` 标签（该文件为 `package main` 独立命令，无标签会
  与包内测试冲突导致无法编译；`go run 显式文件` 不受影响；零逻辑改动）。

### 5.1 批中发现并修复的次生缺陷（fixture 自身隔离漏洞）

首轮 5× 全量运行时发现：运行 2–5 的日志文件头部被 NUL 字节覆盖、
前 ~10 个包的结果行丢失（每个文件恰被改写为同一尺寸）。取证结论：
`go test ./...` 在 `GATE_LOG_FILE` 环境下运行门禁脚本时，**退出码回归
fixture 继承了该环境变量**；Case A / C / D 的内部 `gate_command.sh`
调用因此进入日志模式，把假命令输出 `>`（O_TRUNC）到外层全量日志文件，
外层 `go test` 继续在既有 fd 偏移写入 ⇒ 文件头出现 NUL 空洞。
测试退出码本身不受影响（5 次全量均为 exit 0），但证据日志被污染。
修复：`runGate` 在构造子进程环境前**无条件剥离继承的 `GATE_LOG_FILE`**，
日志模式用例改为显式私有传入；并新增 `TestGate_FixtureNeverTouchesOuterLogFile`
把该失败模式固化为回归测试。修复后 5× 全量复跑：5/5 exit 0、
49 包全绿、0 FAIL 行、日志完整性逐份校验通过（无 NUL）。
