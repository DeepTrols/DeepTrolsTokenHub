## 0. 实现方式

核心资金路径数据契约，按 TDD（RED→GREEN）：先写

**列审计结论**：`payment_orders` 已具备回调与对账身份（`order_no`、
`gateway_trade_no`、`channel`、`pay_method`、`amount`、`notify_raw`、
时间戳），缺的是**查单重试与人工复核元数据**。按 Scope 只做可空增量：

1. 迁移 `000037_payment_order_provider_metadata`（up/down 成对）：
   - `query_attempts INTEGER` — 查单尝试次数（NULL=从未查过）；
   - `last_query_at TIMESTAMPTZ` — 最近一次查单时间；
   - `next_retry_at TIMESTAMPTZ` — 补偿/查单 worker 的下次重试调度点
     （NULL=无调度），附部分索引 `idx_payment_orders_next_retry
     (next_retry_at) WHERE next_retry_at IS NOT NULL`；
   - `review_reason TEXT` — 人工复核标记原因（如金额不一致）。
   全部可空、无回填，旧行保持 NULL 完全可读（backfill-safe）。
   down 迁移按相反顺序 DROP 四列与索引，已在集成测试中实测往返。
2. `Order` 增加四个指针字段（NULL→nil，绝不产生伪造零值），
   `orderCols`/`scanOrder` 同步扩展；`Create` 保持原 INSERT（新订单
   元数据为 NULL=「从未查过」语义）。
3. 仓储写入路径（供后续查单/补偿/复核消费）：
   `RecordProviderQuery(id, nextRetryAt)` 自增计数 + 打点 + 调度/清除，
   `SetReviewReason(id, reason)` 标记/清除复核；两者**只改元数据列，
   绝不触碰 status/amount**，未知订单返回 `ErrNotFound` 失败关闭。
4. console DTO（`toOrderDTO`）：四字段全部 `omitempty`，旧行/未查单行
   序列化为键缺省（合法 JSON），AC-03 无 panic。

### Provider 元数据字段文档（Documentation Requirement）

| 字段 | 类型 | 语义 | 消费方 |
|---|---|---|---|
| `query_attempts` | int 可空 | 已执行的提供方查单次数；NULL=从未 | 查单/补偿 worker（TH-P1-CW-*） |
| `last_query_at` | timestamptz 可空 | 最近一次查单时刻 | 查单/补偿可观测 |
| `next_retry_at` | timestamptz 可空 | 下次允许重试时刻；NULL=无调度 | 补偿调度（部分索引） |
| `review_reason` | text 可空 | 人工复核原因；NULL=未标记 | 对账/复核（配合 TH-P1-02 `no_action`） |

回调/对账身份沿用既有列：`order_no` + `gateway_trade_no` + `channel` +
`pay_method` + `amount`。敏感元数据（`notify_raw` 等）不进日志的约束
保持不变。
