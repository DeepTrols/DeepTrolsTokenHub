## 0. 实现方式

核心资金路径，按 TDD（RED→GREEN）：先写 `notify_route_test.go`
（7 用例）令其编译失败，再实现解析器与路由接线。

设计决策：

1. `channelForRoute` 封闭集解析：`epay` / `alipay` / `wechatpay` 通过；
   其余（含空串、`"Epay"`、`"epay "`）→ `ErrInvalidChannel`，未知路由
   永远到不了验签或结算。
2. `HandleNotifyForChannel(ctx, routeChannel, params)` 顺序：
   路由解析 → 按 `out_trade_no` 查订单 → **订单持久化渠道与路由渠道
   匹配**（空渠道按历史默认 epay）→ 不匹配即 `ErrChannelMismatch`
   拒绝，发生在签名验证与钱包结算**之前**（AC-02）→ 之后才走验签、
   金额核对、过期处理、幂等入账（与回调路径原有守卫完全一致）。
3. `gatewayForRoute`：按**路由渠道**（而非当前全局设置）构造网关 ——
   通道切换期间历史订单继续通过其原始渠道结算；provider adapter 未
   落地 → `ErrChannelNotReady` → handler 返回失败文本，订单保持
   pending（AC-03）。
4. 旧入口 `HandleNotify` 委托到 epay 渠道解析，行为兼容（回归保持绿）。
5. 可观测性：新增 `payment_notify_route_mismatch_total{route,
   order_channel}`；两个标签均经 `SanitizePaymentRoute` 白名单
   （epay/alipay/wechatpay，其余 clamp 为 other），订单号与报文内容
   绝不进入标签。
