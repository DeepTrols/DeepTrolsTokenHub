## 二、🔴 严重问题（资金安全 / 数据安全）

### 1. 无限充值漏洞：`POST /api/console/wallet/topup` 无任何支付验证
`internal/handler/console/wallet.go:340` — 任意已登录用户 POST 任意正数金额即可直接加余额。README 声称"在线充值"，但**没有任何支付网关、订单校验、管理员审批或金额上限**。这是最直接的资金漏洞。

### 2. 假兑换码系统 = 无限造币
`internal/handler/console/wallet.go:143` — 注释自认："accept any well-formed code"。任何 ≥6 位代码兑换 10 元、`DEEP-` 前缀 50 元、`VIP-` 前缀 100 元。无 `redeem_codes` 表、无发放记录、无核销状态。注册用户换一个 code 就能无限充值（幂等键按 code+user，换 code 即绕过）。

### 3. 注册即送 1000 元 / 管理员 10000 元
- `internal/handler/console/auth.go:338`：注册自动赠送 1000 元余额
- `cmd/api/main.go:250`：管理员钱包 10000 元
均无开关、无环境变量控制，生产部署默认生效。

### 4. docker-compose.yml 硬编码生产密钥（全部提交在仓库中）
`docker-compose.yml:55-60`：
- `JWT_SECRET: change-me-in-production-jwt-secret`（公开弱密钥 → 可伪造任意用户 JWT）
- `ENCRYPTION_KEY: abcdefghijklmnopqrstuvwxyz123456`（公开 → 可解密所有 API Key）
- `ADMIN_PASSWORD: deeptrols@2026`（公开 → 可登录管理员）
- PostgreSQL 弱密码、Redis 无密码且端口全暴露
任何拿到仓库的人可伪造管理员身份、解密全部 API Key。

### 5. API Key "6 边界治理" 实际零 enforcement（核心安全承诺落空）
`internal/domain/apikey.go` 定义了 `AllowedModels / SourceWhitelist / CumulativeLimit / WeeklyLimit / MonthlyLimit / OverLimitAction`，console 支持 CRUD，`api_key_spend` 表与 `GetSpend/UpdateSpend` 已建好——但**网关执行链路（chat/completions）完全不检查**：
- 模型白名单只影响 `GET /v1/models` 列表展示（`gateway/models.go:80`），**调用时任意模型可用**
- IP 白名单 / 累计限额 / 周限额 / 月限额 / 超限动作 **全部不生效**
`IsUsable()` 只检查 status。README 与 CLAUDE.md 的核心安全特性是"只读摆设"。

### 6. 无钱包用户 fail-open = 免费调用
`internal/handler/gateway/chat.go:166`：`if wallet != nil { ...reserve... }` — 无钱包用户跳过预算预留直接调用上游。2026-08-04 审计报告已指出（"必须拦截"），**至今未修复**。

### 7. 实际扣费 = 预估 hold 金额，而非真实费用（平台持续亏损）
`chat.go` 流程：按预估 usage 计算 hold → `Reserve` → 上游执行 → `Commit` 扣的是 **reserve 时的 holdAmount**。真实费用 `actualCosts.ListCost` 只写入 usage_log，**不参与扣款，也无补扣机制**（reconciler 只报差异不修复）。
攻击向量：请求 `max_tokens` 巨大 + 输入极小 → hold 仅 0.0001 元 → 实际消耗大量 token → 平台亏本。**这是计费闭环的核心缺陷。**

### 8. 幂等键跨用户碰撞（跨用户扣款风险）
`internal/repository/wallet/postgres.go:395`：`findIdempotentTx` 查询 `WHERE idempotency_key = $1` **不带 wallet_id 过滤**；schema 中 `idempotency_key` 为全局 UNIQUE（`000001_init.up.sql:183`）。
两个不同用户使用相同 `X-Request-ID`（客户端可控）时：第二个用户拿到第一个用户的 transaction，`Commit` 时从**第一个用户**钱包扣款，自己分文不付。应改为 `UNIQUE(wallet_id, idempotency_key)` 且查询带 wallet 过滤。

### 9. 响应缓存跨租户共享
`internal/service/cache/response_cache.go:47` `BuildKey` 只含 `model + messages + 参数`，**不含 tenant/user 维度**。不同租户/用户相同请求共享缓存响应（且命中零计费）。内容相同即共享 → 隐私泄露 + 计费绕过。

### 10. 前端把 API Key 明文永久存入 localStorage
`web/src/pages/APIKeys.tsx:113`：查看明文后写入 `localStorage["api_key_secrets"]`（供 Playground 使用）。违背"仅一次查看"承诺，任何 XSS 即可窃取全部 Key。应改为一次性返回 + 内存态，禁止落盘。

## 三、🟠 高严重问题（功能失效 / 运维）

### 11. Docker 一键部署中 Worker 完全缺失
`docker-compose.yml` 只有 api/web/postgres/redis/litellm 5 个服务，**没有 worker 服务**。README 声称的"Worker 后台任务（计费提交/健康检查/对账）"在 Docker 部署下**永远不会运行**。Dockerfile 也只构建 `cmd/api`（`./cmd/api`），不构建 `cmd/worker`。

### 12. Durable Outbox 是死代码
`outbox_events` 表 + Committer worker（100% 测试覆盖）存在，但**生产代码没有任何地方写入 outbox**（grep 确认，计费是同步 Reserve/Commit）。Committer 永远空转。README 声称的"Durable Outbox 异步计费"与实际不符；且存在**两套计费路径**（同步 + outbox），语义混乱，未来维护是大坑。

### 13. ResponseCache 初始化 bug：缓存功能永远禁用
`internal/app/app.go:106`：`a.ResponseCache = cache.New(a.Redis, ...)` 在 `initRateLimiter`（第 110 行，唯一设置 `a.Redis` 的地方）**之前**执行，此时 `a.Redis` 恒为 nil → `cache.New(nil)` → `IsEnabled()` 恒 false。**README 声称的"响应缓存（SHA256→Redis 零计费）"实际从未生效过。**

### 14. JWT 无状态撤销：被删/被禁用用户 token 24h 内仍有效
`internal/handler/middleware/auth.go`：`ConsoleAuth` 只解析 claims，不查用户当前状态；`AdminAuth` 只检查 claims.Role。用户被禁用/删除/降级后，已有 JWT 仍可访问管理端（角色降级不实时生效）。

### 15. 流式 SSE 64KB 截断 + `[DONE]` 伪装成功（不变量 5 仍违反）
`internal/handler/gateway/chat.go:396`：`bufio.Scanner` 默认 64KB 行上限，长输出（>64KB 单行）触发 `ErrTooLong` → 但此时已向客户端写入 200 + `[DONE]`。客户端判定成功，服务端却走 error 分支 release。`[DONE]` 无条件发送的问题依旧（2026-08-04 审计报告已列，未修复）。

### 16. 非流式 10MB 响应截断
`internal/service/gateway/executor.go:76`：`io.LimitReader(resp.Body, 10<<20)` — 超长响应被截断 → json.Unmarshal 失败 → 整请求报错并释放预留。超长文本生成场景直接失败。

### 17. 租户 DB 故障 fail-open + 无点主机名绕过
`internal/handler/middleware/tenant.go:32`：注释明确 "DB error → fail-open"；`isPlatformHost`（第 49 行）允许**无点主机名**（如内网服务名）绕过租户隔离，生产环境 Host 头伪造可落到平台。

### 18. 钱包扣款与 usage 记录非同一事务
`chat.go`：`Charger.Commit`（钱包事务）与 `Logger.Record`（usage 三表事务）是**两个独立事务**。Commit 成功 + Record 失败 → 钱扣了没记录；反之亦然。对账 L0 只能发现，不能自动修复。

### 19. 配额 Check→Deduct 无预留（TOCTOU 竞态，可透支）
`internal/service/billing/quota.go`：`Check` 只读 remaining 判断，**不锁定/预留**；多个并发请求可通过检查后同时 `Deduct`（best-effort 后台 goroutine）→ 配额超额消费。Deduct 失败仅打日志，无重试。

### 20. 路由无重试/failover + "负载均衡"是静态公式
- `internal/service/gateway/router.go`：选中一个 channel/instance 后直接调用，上游失败即返回错误，**无下一个候选重试**；`FallbackNextPolicy` 注释自认 "not yet implemented"
- `selectWeightedLeastLoad` = `weight/(maxConcurrency+1)`，**不含 CurrentLoad**（审计报告称"读 DB current_load"，实际连读都没读）；instance 选择虽比较 CurrentLoad，但该字段无人更新（仅 health checker 每 60s 两级更新）

## 十二、更正与补充（2026-08-05 追加）

> 本文档生成后，下述事实性表述经核实需要更正。按版本策略以追加方式记录，不改动上文。

### 更正 1：Worker 服务与二进制（对应上文第 69 行）

原文："`docker-compose.yml` 只有 api/web/postgres/redis/litellm 5 个服务，**没有 worker 服务**……`Dockerfile` 也只构建 `cmd/api`，不构建 `cmd/worker`。"

**实况**：`docker-compose.yml` 定义 **6 个服务（含 `worker`）**，`Dockerfile` 同时构建 `cmd/api`（→ `/app/server`）与 `cmd/worker`（→ `/app/worker`）。审计时 worker 容器未运行的直接原因是**容器未被创建/启动**，而非服务或二进制缺失。

**后续发现并修复**：worker 服务存在**入口配置 bug**——Dockerfile `ENTRYPOINT ["./server"]` + compose `command: ["./worker"]` 组合成 `./server ./worker`，即使启动也跑的是 API server 而非 worker。已于 2026-08-05 修复（worker 服务改用 `entrypoint: ["./worker"]`），health_checker / reconciler 现已真正运行。

### 更正 2：健康检查超时（上文第 113 行 vs 第 230 行自相矛盾）

第 113 行把"health_checker 用 `http.DefaultClient` 无超时"列为未修问题，第 230 行又登记"健康检查超时 ✅ 已改用 10s 超时"。**两处矛盾**：实际代码 `checker.go` 已使用 `http.Client{Timeout: 10s}`。以第 230 行"已修复"为准，第 113 行为遗留问题表格未同步。

### 更正 3：健康检查探针语义（2026-08-05 新增修复）

修复前 `probeHealth` 要求 `{base_url}/health` 返回 2xx，但 OpenAI 兼容上游（DeepSeek / 阿里云 MaaS / DashScope）返回 **401（需认证）或 404（无该路径）** → **38 个渠道全部被标为不健康** → 路由报 "No provider channel"。修复后：**2xx/3xx/4xx 均视为可达**（证明上游在线），仅 5xx 或传输层错误（超时 / DNS / 连接拒绝）标记不健康。
